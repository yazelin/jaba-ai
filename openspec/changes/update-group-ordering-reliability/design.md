# 設計說明

## 訊息處理流程（改後）

```
收到群組文字訊息
  │
  ├─ 正規化：去掉 @呷爸（LINE mention 的 isSelf）、全形轉半形、去頭尾空白
  ├─ 取得群組鎖（同一群組一次處理一則）
  ├─ 進行中的單不是今天開的 → 先自動結單（不另外發訊息）
  │
  ├─ 1. 快捷指令：開單／請開單、收單／結單、菜單、目前訂單、help／呷爸
  ├─ 2. 管理員指令（點餐中也生效）：店名、XX菜單、加／移除／清除、今日、改價
  ├─ 3. 明顯不是點餐 → 略過（開頭 @ 其他人、含網址、超過 60 字且沒有菜單品項）
  ├─ 4. 規則解析器能完整解析 → 程式直接寫入訂單
  │       └─ 沒開單：今日店家已設定 → 自動開單後寫入；未設定 → 暫存並提醒一次
  ├─ 5. 點餐中、規則解析不了 → AI 解析意圖 → 程式驗證後寫入
  └─ 6. 沒開單、規則解析不了 → 只有叫呷爸時才回應（維持現狀）
  │
  └─ 回覆：訂單有變動時，由資料庫產生本人確認行
```

## 規則解析器（`app/services/order_parser.py`）

純函式，輸入「訊息文字＋今日菜單」，輸出結構化動作或「解析不了」。不碰資料庫，方便測試。

支援的寫法（全部取自歷史訊息）：

| 寫法 | 範例 | 動作 |
|---|---|---|
| 品項 | `炸排骨飯`、`宮保雞丁` | 加 1 份 |
| 品項＋數量 | `炸排骨+1`、`銷魂飯*5`、`古早味排骨 x4`、`黯然飯×3` | 加 n 份 |
| 帶價格 | `鹹豬肉 $105 +1`、`椒鹽雞塊飯/麵 $95（飯）` | 價格忽略，以菜單為準 |
| 代訂 | `銷魂飯(小李)*1`、`椒鹽雞塊*3 (老闆)`、`同事B:古早味排骨*1`、`小李：銷魂飯` | 加在發訊息者名下，note 記代訂人 |
| 多品項 | 換行分隔、空白分隔、`黯然飯*3+銷魂飯*1` | 逐項處理 |
| 減少 | `少一個蔥油雞`、`炸排骨少3個`、`銷魂飯少兩個`、`-2` | 減 n 份，不夠就刪到 0 |
| 取消 | `取消`、`幫我取消`、`我不要炸雞腿飯了`、`取消 黯然飯` | 有品項就刪該品項，沒品項就刪本人整筆 |
| 改 | `改炸雞腿`、`蔥油雞*3改蔥爆豬*3` | 刪舊加新 |
| 選項回覆 | `飯`、`便當啦`、`單點` | 回答上一題追問 |

「+」的判斷：後面接數字是數量（`炸排骨+1`），後面接品項是分隔（`玫瑰油雞+味噌湯`）。

品項比對順序：完全相符 → 去掉「飯／便當／麵」後相符 → 包含且唯一 → 常見錯字表（宮本→宮保、販→飯）。多個候選時回一題編號選擇；完全找不到時交給 AI。

數量上限 20，超過就交給 AI，避免 `炸排骨+100` 這類誤觸直接寫入。

## 重傳與重列

歷史訊息裡常見兩種重複：機器人沒回就再傳一次（07-13「奇怪，怎麼老漏單」），以及把整份清單重貼一次（06-08）。
規則：這則訊息包含本人原本點的每一項、**數量完全相同**，就不重複加，並提醒「要多一份請打再加一個」。
數量不同就當追加：08-13「銷魂飯」之後「銷魂飯*3」實際是再幫別人點 3 份。少算比多算嚴重，而且確認行會顯示總數，點錯可以馬上改。
「再加」「追加」開頭的永遠追加。

歷史重播驗證：40 次點餐中，新流程與實際存下的訂單有 13 次不同，逐一檢查後：
- 8 次是訊息交給 AI（重播不模擬）、菜單後來才有的品項，或使用者在回答舊系統的追問
- 4 次是改善：06-08 不再多算 $330；02-23 補回因為沒回答「飯還是麵」而遺失的訂單；02-02、02-11 記下代訂對象
- 1 次有歧義（04-07「炸雞腿*1」後「炸雞腿*2」，新流程算 3+1=4 份，舊系統當成改成 2 份），確認行會立刻顯示總數

## 預設選項

`飯/麵` 類品項預設飯；有便當、單點兩種價格的品項預設便當。先用「菜單品項第一個選項＝預設」，不加欄位。使用者有明講才用明講的。確認行會寫出用了哪個選項（「炸雞腿便當 $125」），點錯的人看得到，可以直接改。

## AI 路徑

AI 只處理規則解析不了的句子，例如「我想吃炸的最便宜的」「我追加3個椒鹽雞塊飯」。

- 新增 `set_order`：使用者把整份重新列一次時，用它整份重設，不再追加。
- `cancel_order` 只有在當前訊息出現取消、不要、算了這類字時才執行，否則程式拒絕。06-08 的「整筆取消再重點」就會被擋下來。
- 一則訊息同時出現 `cancel_order` 與 `create_order` 時，改用 `set_order` 處理。
- AI 回覆的文字只保留非訂單的部分（例如回答「雙饗銷魂飯是什麼」）。訂單內容一律換成程式產生的確認行。
- 提示詞拿掉「跟單時查看對話歷史中最近一筆成功的訂單」這段，改由程式從 `session_orders` 找最近一筆。

## 確認行

```
同事A：黯然飯×3、雞肉飯×1、銷魂飯×1（小李），小計 $500
```

只列本人。用了預設選項或模糊比對時加一句「（照便當算，要單點再說）」。完整清單只在「目前訂單」與結單時貼出。

## 自動開單、自動關單

- 管理員輸入店名：設定店家，同時開單。如果今天的單已經開著而且有訂單，改成回「目前有 N 筆 XX 的訂單，要換店請先結單」，不自動換。
- 收到任何訊息時，進行中的單如果不是今天開的，就靜默結單。這一條就能解決「舊單卡住」，排程只是補強。
- 排程每天 15:00 結束當天還開著的單；沒有訂單的單直接刪除，不留空 session。

## 開單前的點餐

- 今日店家已設定：自動開單，寫入訂單，回確認行並註明「已自動開單」。
- 今日店家未設定：只有帶數量記號（`+1`、`*n`）的訊息才算點餐，避免把閒聊當訂單。系統回一次「還沒選店家，管理員選好後會把剛剛的點餐補上」（同一天只提醒一次），訊息存在 `chat_messages`（`session_id` 為空）。開單時取當天這些訊息跑一次規則解析，補進訂單，再貼一次補單結果。解析不了的列出來，請本人重點。

## 群組鎖

同一群組的訊息排隊處理（`asyncio.Lock`，以 group_id 為 key）。目前服務是單一行程，這樣就夠；之後如果改成多個 worker，要換成資料庫 advisory lock。

## 不呼叫 AI 的訊息

開頭 @ 其他成員的（付款提醒）、含網址的、超過 60 字且沒有菜單品項的（公告）。歷史資料中這類訊息 AI 也都選擇不回，現在只是省下每則平均 8 秒與誤判的機會。

## 驗證方式

1. 解析器單元測試：用歷史訊息的寫法，改寫成匿名案例（repo 是公開的，不放真實姓名與原文）。
2. 歷史重播（只在本機）：讀 .11 的 `chat_messages`（唯讀），依序餵進新流程，最後跟 `order_items` 比對。差異逐筆列出，人工確認是舊系統錯還是新系統錯。重播腳本放 repo，資料不放。
3. 以 06-08、08-04、11-02、03-03 四天當必過案例。

## 風險

- 規則解析器把閒聊當成點餐：只在點餐中或帶數量記號時才解析，且品項必須對得上今日菜單。
- 自動開單在管理員不想開時被觸發：只有今日店家已設定時才會；設店家本身就代表今天要訂。
- 改動 `_handle_text_message` 分派順序，影響管理員既有習慣：保留所有舊指令，管理員原本的「結單→店名→開單」三步照樣有效。
